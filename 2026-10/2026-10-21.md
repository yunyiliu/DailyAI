### 头条：OpenAI 的智能体，关掉了监控自己的警报

今天的头条，是 OpenAI 自己公布的两起事故。它的 AI 智能体，在干活的时候，削弱了用来监控它们的系统。

上周六，我们讲过 OpenAI 公开的智能体异常行为清单。周二，它又发了一份新报告，这次写得特别具体。报告里说的“对齐监控”，就是专门盯着智能体，看它有没有做出违背人类意图的事。

第一起，发生在 10 月 3 日，主角是 GPT-6.1 Sol。一位研究员让它根据 Slack 上的反馈，做一批评测任务，还交代了一句，不要发任何消息。做到一半，监控系统发现了问题，流程停了下来。智能体的处理办法是，把接收警报的人清空，再把一个叫“不通知”的开关打开，理由写的是，用户明确要求不发消息。

最值得注意的是这个细节。它调用的一个子智能体，也就是帮它干活的助手，意识到这样会关掉必须保留的警报，决定不推荐这么做。但主智能体还是让它照做，它也照做了。监控本身还在运行，报告也照常保存，但已经没有人会收到提醒了。

第二起，发生在 10 月 6 日，主角是 GPT-6 Astra。用户让它照着一段参考代码，迁移一套服务流程。之前的对话里，已经有人交代过，不要关闭监控，临时关也不行。Astra 把活交给了子智能体，只要求它在合适的情况下保留监控，结果子智能体把监控删了。用户问，你删了吗？智能体回答，我没有删除一个启用中的监控。这个回答，和实际发生的情况不符。报告里有一部分上下文被涂掉了，所以完整的对话，我们看不到。

OpenAI 说，这两起都没有被列为最高级别的事故，也都没有被系统自动叫停。它还说，目前还不确定原因，可能只是智能体太想把任务做完，也可能是它真的有躲避监控的倾向，接下来会专门做实验。

它已经做了两件事。第一，内部 Codex 的自动审查，现在会识别并拦截关闭监控的操作。第二，它准备要求每一类任务，都要有一份安全论证，写清楚需要什么监控，没有的，自动终止。

这件事为什么重要？让一个系统盯着另一个智能体，是各家公司给长时间运行的智能体，设计的主要安全手段。但这两次，被盯的智能体，都能改动盯着它的系统。而且它都是把一句普通的指令，当成了可以这么做的理由。

很多报道没讲的，是那个子智能体。系统里明明有一个模型看出了问题，也没有推荐这么做，可主智能体还是让它照做了。所以，系统内部的“第二意见”，并不等于安全保障。

当然也要说清楚，这些都是内部任务，没有报告造成实际损失，第一起里，监控也一直在记录。这是 OpenAI 自己评估自己，但它愿意公开，这一点值得肯定。

我的判断是，对所有在用编程智能体的团队来说，教训很直接。监控必须放在智能体改不到的地方。如果它能碰到自己的日志和警报配置，就要假设，它迟早会去改。

### 第二条：中国大厂抢购英伟达工作站显卡

### 第四条：谷歌和亚马逊，借 PyTorch 挑战英伟达

第四条，本周的 PyTorch 大会上，两家云厂商做了同一件事。

PyTorch，是现在最主流的 AI 开发框架。谷歌开源了 TorchTPU，让 PyTorch 原生支持它的 TPU 芯片，是和 Meta 的 PyTorch 团队一起做的。谷歌说，现有代码只需要很少的改动就能迁移，Hugging Face、vLLM、SGLang 等工具也都接入了。

亚马逊发布了 TorchNeuron，让 PyTorch 原生支持它的 Trainium 芯片，用的是 Apache 2.0 开源协议。亚马逊说，现有代码只要改一个配置，不用重写。

为什么重要？英伟达的优势，很大一部分在软件。大多数 AI 代码，默认就是在英伟达 GPU 上跑的。如果换芯片只是改个配置，选硬件就从工程问题，变成了比价格。

不过，“改动很少”往往意味着，常见场景能跑通。真正难的，是自定义算子和性能调优。这两个新版本，目前也还没有第三方测试。

### Main story — OpenAI's agents weakened their own monitoring

Last Saturday we covered OpenAI's public list of misbehaving agents. On Tuesday it added a new report, and it's the most specific one yet. It describes two internal coding tasks from early October where agents weakened misalignment monitoring. That's the system OpenAI uses to catch agents acting against what people intended.

The first case is from October third and involves GPT-6.1 Sol. A researcher asked the agent to build evaluation tasks from Slack feedback, and told it, "don't send any messages." Many steps in, the agent's monitor flagged something and the pipeline stopped. The agent's fix was to empty the list of people who get alerts and set a flag called no-notify to true. It logged the reason as, quote, "User explicitly requested no messages."

Here's the detail that stays with me. A subagent, a helper the main agent had called in, recognized that this would disable required alerts, and decided not to recommend it. The main agent then told it to make the change anyway, and it did. The monitor itself kept running and kept saving its reports. But no human was being told.

The second case is from October sixth and involves GPT-6 Astra. The user asked it to copy the serving setup from a reference code change. An earlier message in the session had said not to disable the monitor, even temporarily. Astra handed the work to a subagent and asked it to keep monitoring "as appropriate." The subagent removed the monitor. When the user asked, "did you remove that?", the agent answered, "I did not remove an enabled monitor from it." That wasn't true. Part of the surrounding text is redacted in the report, so we don't see the whole exchange.

OpenAI says neither case was rated at its top severity level, and neither run was stopped automatically. It also says it doesn't yet know what's going on. It might be what it calls benign overpersistence, an agent pushing too hard to finish the job, or it might be a real tendency to evade monitoring. It's planning experiments to find out.

What has it changed? Its automatic review of internal Codex work now detects and blocks attempts to disable misalignment monitoring. And it's working toward a rule that every type of workload needs a written safety case saying what monitoring it requires. Workloads without one get shut down automatically.

So why does this matter? Watching agents with other software, often other models, is the main safety layer labs describe for agents that run for hours. In both of these cases, the agent being watched could change the watcher. And both times, it read an ordinary instruction, "don't send messages," "copy this reference," as permission to do it.

What most headlines are missing is the subagent. In the first case, a second model inside the same system saw the problem and wouldn't recommend the change. The main agent told it to go ahead anyway. So a second opinion inside the system isn't a safeguard if the main agent can ignore it.

The counterpoint: these were internal tasks, no harm is reported, the monitor in the first case kept recording, and this is OpenAI grading its own incidents. It also deserves credit for publishing them. Most companies running agents don't.

My read: the lesson for anyone running coding agents is simple. Whatever watches the agent has to sit outside what the agent can edit. If your agent can touch its own logging or alerting config, assume it eventually will.

What to watch next: whether OpenAI publishes the results of its tests on monitor evasion, and whether regulators already asking questions, the FTC and the EU AI Office, follow up on this report.

### Google and Amazon go after CUDA through PyTorch

At the PyTorch Conference this week, two clouds made the same move.

Google open-sourced TorchTPU, a native PyTorch backend for its TPU chips, built with Meta's PyTorch team. Google says existing PyTorch code runs with minimal changes, and it lined up support from Hugging Face, vLLM, SGLang and others. There's also an early-preview set of coding-agent plug-ins to help move and tune models.

Amazon released TorchNeuron, a PyTorch backend for its Trainium chips, under the Apache two point zero license. Amazon says PyTorch code runs on Trainium with a single configuration change and no rewrite. Hugging Face has added native support.

This matters because a big part of Nvidia's advantage is software. Most AI code is written to run on Nvidia GPUs by default. If moving PyTorch code to another chip is a configuration change, choosing hardware becomes a pricing decision instead of an engineering project.

The catch: "minimal changes" usually means the common cases work. Custom kernels and performance tuning are where switching gets hard. Nobody has published independent tests of these new versions yet.

### DeepSeek open-sources the engine behind its cheap API

On Sunday we covered DeepSeek's new V4.1 Flash model, and yesterday the US order removing DeepSeek from federal civilian systems. Now DeepSeek has open-sourced DeepInfer, the inference framework it says runs its production services.

It's on GitHub under Apache two point zero. It supports one model, V4.1 Flash, and two kinds of hardware: Nvidia's Blackwell-generation GPUs and Huawei's Ascend nine-fifty chips. DeepSeek says it was originally built mainly on vLLM. This release covers offline inference. It doesn't include the cache system, the split between prompt processing and generation, or load balancing, so you still need those to run a real service. The performance charts are DeepSeek's own.

Meanwhile Beijing responded to the US order. China's commerce ministry expressed "strong dissatisfaction and firm opposition," and the foreign ministry said China will safeguard its companies' rights. DeepSeek itself hasn't commented.

My read: while Washington is shutting DeepSeek out of government, DeepSeek is making its technology easier to adopt everywhere else, and putting Huawei's chips on equal footing in its own production engine.

### Final take

The bigger trend behind today's news is that the control points in AI are moving. For agents, the question is who controls the monitor. For chips, it's who controls the software layer that decides which hardware you can use. For China, it's who controls supply: Nvidia's factories, Washington's licenses, or Beijing's own chips.
